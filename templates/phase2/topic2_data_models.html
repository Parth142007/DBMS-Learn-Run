2. Data Models in DBMS

Explore the conceptual blueprints of database design — from historical hierarchical trees and network graphs to modern relational tables, conceptual ER models, and object-oriented paradigms.

What is a Data Model and Why is it Fundamental?

A Data Model is an abstract framework and collection of conceptual tools used to describe:

Data Structure
How data entities and attributes are arranged
Relationships
How different entities associate with one another
Data Semantics
The real-world meaning and context of the data
Constraints
Rules enforcing validity and referential consistency

Just as an architect draws an architectural blueprint before builders pour concrete for a skyscraper, a database designer selects and designs a data model before any SQL tables are created or queries are written. It bridges the gap between human real-world concepts (students, courses, departments) and physical computer storage (bytes, blocks, disk sectors).

2.1

Hierarchical Data Model (Tree-Based)

Developed in the late 1960s (notably by IBM in their Information Management System — IMS for the Apollo space program), the Hierarchical Data Model organizes data into an inverted tree structure.

  • Root Node: The topmost node of the tree with zero parent nodes (e.g., College).
  • Parent Node: A node that branches into one or more dependent child records.
  • Child Node: A record subordinate to a parent. Strict Cardinality Rule: Every child node can have only one parent node (strict 1:N relationship).
  • Leaf Node: A bottom-tier child node that has no further children.
  • Navigation: Data retrieval requires navigating top-down along pre-configured physical pointer paths from the root.
Diagram 2.1: College Hierarchical Data Model Tree

Figure 2.1: In the Hierarchical Model, every student record has exactly ONE parent department. There is no natural way to represent a student enrolled in multiple departments or a course taught across departments without data duplication.

Advantages
  • Simple conceptual design matching natural real-world hierarchies (e.g. corporate org charts, file folder trees).
  • Very fast retrieval when searching down defined 1:N tree paths via fixed pointers.
  • Enforces strict referential integrity natively (a child cannot exist without its parent).
Severe Limitations
  • Cannot represent M:N relationships: If a student takes courses in two departments, the student record must be duplicated under both parents.
  • Deletion Anomaly: If the Electronics department is deleted, all student records under it are automatically wiped out!
  • Rigid Navigation: Querying from child to parent or across tree branches requires complex pointer walking.
Modern Resemblance: File systems (directories contain subdirectories and files) and XML / JSON hierarchical document trees operate on this exact hierarchical principle.
2.2

Network Data Model (Graph-Based)

Standardized by the CODASYL (Conference on Data Systems Languages) DBTG in 1971, the Network Data Model was invented to overcome the single-parent limitation of the hierarchical model. It models data as a graph rather than a rigid tree.

Key Structural Distinction from Hierarchical:

In the network model, a child record (referred to as a Member) can have multiple parent records (referred to as Owners). Relationships are known as Sets and are maintained using bidirectional pointer circular chains.

Diagram 2.2: Many-to-Many Record Links in the Network Model

Figure 2.2: A child record can belong to multiple parent record sets. Alice is enrolled in both CS101 and CS202, and CS101 has both Alice and Bob as members. (Note: This illustrates the network model's connected-record concept, distinct from an ER diagram).

Advantages
  • Naturally models complex real-world Many-to-Many (M:N) relationships without duplicating records.
  • Provides flexible access paths — data can be queried starting from courses, students, or departments.
Critical Drawbacks
  • Extreme Internal Complexity: Every relationship requires physical disk pointers (embedded memory addresses). If a pointer breaks, the entire database becomes corrupted.
  • Low Data Independence: Software developers had to understand the physical pointer paths to write database queries. Changing the schema required rewriting application code.
2.3

Relational Data Model (Table-Based)

Proposed by British computer scientist Dr. Edgar F. Codd in 1970 at IBM, the Relational Data Model revolutionized the database industry and remains the undisputed global foundation for modern systems (MySQL, PostgreSQL, Oracle, SQL Server).

Instead of navigating rigid pointer chains or tree paths, the relational model stores data in intuitive, two-dimensional Tables (Relations).

Table ↔ Relation A 2D matrix of rows and columns storing records of an entity type.
Row ↔ Tuple A single horizontal record representing one unique real-world instance.
Column ↔ Attribute A vertical property or characteristic describing the entity (e.g., GPA).
Domain The permissible set of atomic values for a column (e.g. GPA between 0.0-10.0).
Concrete Relational Tables Walkthrough

Notice how relationships are established — not with physical memory pointers, but purely by sharing matching attribute values across tables!

How the Relational Link Works: Aarav (Roll 2026CS01) has dept_id = 1. By matching this value against the primary key dept_id = 1 of the departments relation, the system knows Aarav belongs to Computer Science in Turing Block without needing any pointer hard-coded in disk memory.
Why Relational Model is Universally Dominant:
  • Declarative Querying: Using SQL, you declare what data you want, not how to physically retrieve it from disk sectors.
  • High Data Independence: Internal storage reorganization does not affect application queries.
  • Mathematical Foundation: Built on set theory and first-order predicate logic, providing provable data integrity.
Limitations:
  • Rigid tabular schema can be inefficient for highly unstructured or nested hierarchical data (e.g. CAD drawings, deep JSON documents).
  • Large relational queries requiring multi-table lookups can introduce CPU overhead compared to direct in-memory graph pointers.
2.4

Entity-Relationship (ER) Model (Conceptual)

Proposed by Peter Chen in 1976, the Entity-Relationship (ER) Model is a high-level conceptual modeling tool used during the preliminary database planning phase.

Phase Boundary Reminder: Here we introduce the conceptual basics (Entity, Attribute, Relationship) so you understand what an ER model is. Detailed ER modeling, cardinality ratios, and relational mapping belong to Phase 6.
1. Entity

Represented by a Rectangle

A real-world distinguishable person, place, or concept with independent existence. Examples: Student, Course, Department.

2. Attribute

Represented by an Oval / Ellipse

A descriptive characteristic or property of an entity. Examples: roll_no, name, credits.

3. Relationship

Represented by a Diamond

An association between two or more entities. Example: A student Enrolls_In a course.

2.5

Object-Oriented Data Model (OODM)

The Object-Oriented Data Model merges Object-Oriented Programming (OOP) paradigms with database management capabilities.

In traditional relational databases, data is strictly passive (tables store numbers and strings, while application code executes separately). In an Object-Oriented database, data and the operations that mutate it are packaged together into a single unit called an Object.

Objects & Classes A class defines the blueprint; an object is an instance with state and behavior.
Encapsulation Attributes (internal state) can only be accessed through defined methods (behavior).
Inheritance Subclasses inherit attributes and methods (e.g. GraduateStudent extends Student).
Object ID (OID) Every object has a persistent, system-generated unique ID independent of its values.
Diagram 2.4: Object-Oriented Representation of Student Entity
Class: Student
// Attributes (State): - student_id: Long
- full_name: String
- enrolled_courses: List<Course>
- semester_grades: Map<Course, Float>
// Methods (Behavior): + calculateGPA(): Float
+ enrollCourse(c: Course): Boolean
+ generateGradeReport(): PDF

Figure 2.4: Unlike relational rows, the Student object encapsulates both properties (grades) and computational methods (calculateGPA()).

Primary Use Cases: Computer-Aided Design (CAD/CAM), Geographic Information Systems (GIS with spatial geometries), complex 3D simulation models, and multimedia streaming architectures.

2.7

How to Choose an Appropriate Data Model

In enterprise software engineering, no single data model is a universal silver bullet. Different business domains require different structural trade-offs:

Scenario A
University Administration & Banking Portals

Recommended: Relational Data Model. Structured transactions, tabular grade sheets, ACID guarantees, and ad-hoc SQL reporting make relational databases the optimal choice.

Scenario B
Database Requirements Gathering & System Blueprint

Recommended: Entity-Relationship (ER) Model. Non-technical business analysts and developers use ER diagrams to agree on entities and business rules before creating tables.

Scenario C
Computer-Aided Design (CAD) & Aeronautical Simulations

Recommended: Object-Oriented Model. 3D geometry coordinates, mathematical transformations, and nested component assemblies are naturally modeled as objects with behavioral methods.

Scenario D
Operating System File Trees & Configuration Storage

Recommended: Hierarchical Model. Hard disk directory trees and JSON/YAML configuration hierarchies have strict 1:N nesting where every folder has exactly one parent.

Model Answer: In the Hierarchical model, data is organized as a tree where every child node can have only one parent node (strict 1:N relationship). In contrast, in the Network model, data is organized as a graph where a child record (member) can have multiple parent records (owners), allowing natural representation of Many-to-Many (M:N) relationships.

Model Answer:
  • Tuple: A single horizontal row in a relation representing a specific real-world record. E.g., (101, 'Aarav', 1, 9.45) in students.
  • Attribute: A named vertical column representing a specific property of the entity. E.g., first_name, gpa.
  • Domain: The permissible set of atomic values for an attribute. E.g., the domain of gpa is decimal numbers from 0.00 to 10.00.
