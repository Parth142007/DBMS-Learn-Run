5. Authorization, Roles & Database Security

Safeguard relational databases against unauthorized access and attacks — explore Authentication vs Authorization, GRANT / REVOKE syntax, MySQL 8 Roles, the Principle of Least Privilege, and defense-in-depth against SQL Injection.

5.1

Authentication vs. Authorization & Least Privilege

Database security operates on two fundamental gatekeeping layers:

Layer 1: Authentication (Identity)
"Who are you?"

Verifies client identity using credentials (username, password hash, SSL/TLS certificate, or PAM plugin). In MySQL, an account is identified by both name and host: 'username'@'hostname'.

Layer 2: Authorization (Permissions)
"What are you allowed to do?"

Determines which specific operations (SELECT, INSERT, DROP) an authenticated user may perform on specific database objects (databases, tables, views, columns).

The Principle of Least Privilege (PoLP)

Every process, user, and web application service must be granted only the minimum set of privileges strictly required to complete its legitimate business purpose — and nothing more!

Why Never Connect Applications as 'root'? If a web application connects to MySQL as 'root'@'localhost', any SQL injection vulnerability gives the attacker complete control to drop the entire database, create backdoor accounts, or read server files.

5.2

User Management: GRANT & REVOKE Syntax

MySQL manages permissions through Data Control Language (DCL) statements:

Privilege Scope Levels
Scope Level Syntax Pattern Description
Global ON *.* Applies to all databases and all tables on the MySQL server instance.
Database Level ON college_db.* Applies to all existing and future tables/views within college_db.
Table Level ON college_db.students Restricted strictly to the designated table.
Column Level SELECT (roll_no, first_name) ON ... Finest granularity — restricts reading to specific non-sensitive columns.
-- 1. Create a dedicated application user account CREATE USER 'web_app_user'@'192.168.1.%' IDENTIFIED BY 'StrongSecretPwd#2024'; -- 2. Grant read-only access to views and select on students GRANT SELECT ON college_db.vw_student_mentorship TO 'web_app_user'@'192.168.1.%'; GRANT SELECT, INSERT ON college_db.registrations TO 'web_app_user'@'192.168.1.%'; -- 3. Inspect granted permissions SHOW GRANTS FOR 'web_app_user'@'192.168.1.%'; -- 4. Revoke insert capability if policy changes REVOKE INSERT ON college_db.registrations FROM 'web_app_user'@'192.168.1.%';
5.3

MySQL 8 Roles: Role-Based Access Control (RBAC)

In large production environments with dozens of microservices and hundreds of developers, granting privileges individually to every account is error-prone. MySQL 8 introduced native Roles — named collections of privileges that can be granted to users:

Step 1: Create Role
CREATE ROLE 'student_auditor';
Step 2: Assign Privileges
GRANT SELECT ON college_db.* TO 'student_auditor';
Step 3: Bind to User
GRANT 'student_auditor' TO 'alice'@'%';
Role Activation in MySQL 8: By default, when a user logs in, their assigned roles are not active until enabled, or unless configured via: SET DEFAULT ROLE ALL TO 'alice'@'%';.
5.4

SQL Injection Defense & Parameterized Queries

SQL Injection (SQLi) occurs when untrusted user input is directly concatenated into a dynamic SQL query string without sanitization, allowing an adversary to alter query syntax and execute arbitrary commands.

INSECURE: String Concatenation
# Python / Flask vulnerability: user_input = "' OR '1'='1" query = f"SELECT * FROM users WHERE roll = '{user_input}'" # Evaluates to: # SELECT * FROM users WHERE roll = '' OR '1'='1' cursor.execute(query) # Leaks entire table!

Treats malicious input text as executable SQL code instructions.

SECURE: Parameterized Query
# Safe parameterized query used in our project: user_input = "' OR '1'='1" query = "SELECT * FROM users WHERE roll = %s" # Sent as separate protocol message: cursor.execute(query, (user_input,))

MySQL precompiles query grammar first. Input is treated strictly as literal data.
