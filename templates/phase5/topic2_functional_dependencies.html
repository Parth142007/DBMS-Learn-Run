2. Functional Dependencies & Candidate Keys

Master the formal language of relational schema constraints — discover what functional dependencies mean, explore Determinants and Dependents, and classify dependencies into Trivial, Full, Partial, and Transitive.

2.1

What is a Functional Dependency?

Let $R$ be a relational schema, and let $X$ and $Y$ be subsets of attributes in $R$. A functional dependency, denoted by:

X → Y (Read as: "X functionally determines Y", or "Y is functionally dependent on X")

Formal Definition: In any legal relational state $r(R)$, for every pair of tuples $t_1, t_2 \in r$:

If   t1[X] = t2[X],   then   t1[Y] = t2[Y].

In plain English: If you know the value of attribute set $X$, there is exactly one corresponding value of attribute set $Y$.

Left-Hand Side (LHS)
Determinant (X)

The attribute or set of attributes whose values uniquely determine the values of the dependent attributes.

Right-Hand Side (RHS)
Dependent (Y)

The attribute or set of attributes whose value is uniquely determined by the determinant.

Crucial Relational Rule: FDs Cannot Be Inferred from Sample Rows Alone! A sample instance of a table can demonstrate that a functional dependency does NOT hold (by showing a counterexample with identical $X$ but differing $Y$). However, you can never prove that an FD holds purely by inspecting current rows! Functional dependencies are enterprise business rules and physical integrity constraints defined by the real-world domain.
2.2

Classification of Functional Dependencies

Trivial vs. Non-Trivial FDs

Trivial: $X \to Y$ is trivial if $Y \subseteq X$. For example, (StudentID, CourseID) → StudentID is always guaranteed to hold mathematically because $StudentID$ is already inside the determinant!

Non-Trivial: $X \to Y$ is non-trivial if $Y \not\subseteq X$. It is completely non-trivial if $X \cap Y = \emptyset$.

Full vs. Partial Dependencies

Full Dependency: $Y$ is fully functionally dependent on $X$ if removing any attribute from $X$ causes the dependency to no longer hold. E.g. (StudentID, CourseID) → Grade.

Partial Dependency: An attribute $Y$ depends on a proper subset of a composite key $X$. E.g. (StudentID, CourseID) → StudentName is partial because StudentID → StudentName holds alone!

Transitive Functional Dependency ($X \to Y \to Z$)

A functional dependency $X \to Z$ is transitive if there exists an attribute or set $Y$ such that:

X → Y    AND    Y → Z    (where Y does not determine X, and Z is not a subset of Y)

Student-Department Example:
In STUDENT(StudentID, StudentName, DepartmentID, DepartmentName):
1. StudentID → DepartmentID (Each student belongs to one department)
2. DepartmentID → DepartmentName (Each department has one unique name)
⇒ Therefore, StudentID → DepartmentName is a transitive dependency!

Practice Exercises

Exercise 2.1 Partial Dependency Check

Library Loan System:

Given relation BOOK_LOAN(BookID, MemberID, DueDate, BookTitle, MemberName) with candidate key (BookID, MemberID). Identify which dependencies are full and which are partial.

Hint:
• (BookID, MemberID) → DueDate is a Full Functional Dependency.
• BookID → BookTitle and MemberID → MemberName are Partial Dependencies because they depend on parts of the primary key!
Exercise 2.2 Transitive Dependency

Order Processing System:

In relation ORDERS(OrderID, OrderDate, CustomerID, CustomerCity, ShippingRate) where OrderID → CustomerID, CustomerID → CustomerCity, and CustomerCity → ShippingRate. Trace the transitive dependency chain starting from OrderID.

Hint: OrderID → CustomerID → CustomerCity → ShippingRate. The primary key OrderID determines ShippingRate transitively through CustomerID and CustomerCity!
