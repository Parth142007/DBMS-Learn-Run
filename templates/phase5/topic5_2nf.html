5. Second Normal Form (2NF) & Partial Dependencies

Eliminate partial functional dependencies on composite candidate keys — understand Prime vs. Non-Prime attributes, diagnose 2NF violations in multi-attribute keys, and decompose relations into pure entity schemas.

5.1

What is Second Normal Form (2NF)?

A relational schema $R$ is in Second Normal Form (2NF) if and only if:

  1. It is already in First Normal Form (1NF).
  2. No Partial Dependencies: Every non-prime attribute is fully functionally dependent on every candidate key of $R$.
Prime vs. Non-Prime Attributes:
Prime Attribute
Part of a Key

An attribute that belongs to at least one candidate key of the relation. (e.g. StudentID and CourseID in composite key (StudentID, CourseID)).

Non-Prime Attribute
Descriptive Attribute

An attribute that does NOT belong to any candidate key. (e.g. StudentName, CourseName, Grade).

Relational Theorem: Single-Attribute Keys Guarantee 2NF! If every candidate key of a 1NF relation consists of a single attribute (not composite), the relation is automatically in 2NF! Partial dependencies are mathematically impossible because a single-attribute key has no proper subsets!
5.2

Case Study: The 2NF Enrollment Violation

Consider the 1NF table ENROLLMENT created in Lesson 4:

ENROLLMENT(StudentID, CourseID, StudentName, CourseName, Grade)

Assumed Domain Business Rules (Functional Dependencies):

1. (StudentID, CourseID) → Grade          Full Dependency (Valid)
2. StudentID → StudentName                Partial Dependency (Violates 2NF!)
3. CourseID → CourseName                  Partial Dependency (Violates 2NF!)
Why it fails 2NF: The Candidate Key is composite: (StudentID, CourseID). The non-prime attribute StudentName depends only on StudentID (a proper subset of the key). Similarly, CourseName depends only on CourseID.
The 2NF Decomposition Solution:

To satisfy 2NF, each partial dependency is extracted into its own independent relation with its determinant as the primary key:

Relation 1: STUDENT
StudentID (PK) StudentName
101Amit
102Neha
FD: StudentID → StudentName (Full key)
Relation 2: COURSE
CourseID (PK) CourseName
C01DBMS
C02Python
FD: CourseID → CourseName (Full key)
Relation 3: ENROLLMENT
StudentID (FK) CourseID (FK) Grade
101C01A
101C02B+
102C01A-
FD: (StudentID, CourseID) → Grade (Pure Full FD)

Practice Exercises

Exercise 5.1 Single vs Composite Keys

Single-Attribute Key 2NF Evaluation:

A table EMPLOYEE(EmpID, Name, DeptID, Salary) has primary key EmpID. Is it possible for this table to violate 2NF? Explain why or why not.

Hint: No! Since the candidate key has only one attribute (EmpID), there are no proper subsets of the key. Therefore, partial dependencies cannot exist, and any 1NF table with a single-attribute candidate key is automatically in 2NF!
Exercise 5.2 Warehouse Inventory Decomposition

Decompose Warehouse Inventory into 2NF:

Given INVENTORY(WarehouseID, ItemID, QtyOnHand, WarehouseCity, ItemDescription) with key (WarehouseID, ItemID). Decompose it into 2NF relations.

Hint:
1. WAREHOUSE(WarehouseID, WarehouseCity) (Determinant: WarehouseID)
2. ITEM(ItemID, ItemDescription) (Determinant: ItemID)
3. INVENTORY(WarehouseID, ItemID, QtyOnHand) (Determinant: (WarehouseID, ItemID))
