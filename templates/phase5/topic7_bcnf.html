7. Boyce-Codd Normal Form (BCNF) & Superkey Enforcements

Understand why BCNF is stricter than 3NF, master the superkey determinant rule, and analyze the classic 3NF-compliant yet BCNF-violating relation with overlapping composite candidate keys.

7.1

Why BCNF? Stricter Than 3NF

Proposed in 1974 by Raymond F. Boyce and Edgar F. Codd, Boyce-Codd Normal Form (often called 3.5NF) addresses an edge case that standard 3NF allows: when a relation possesses multiple overlapping composite candidate keys.

3NF Condition Review

For every non-trivial $X \to A$:

  • $X$ is a superkey, OR
  • $A$ is a prime attribute (part of ANY candidate key).
The prime-attribute clause provides an "escape hatch" that allows redundancy if the dependent attribute happens to be part of another candidate key.
BCNF Condition (Strict)

For every non-trivial functional dependency $X \to A$:

$X$ MUST be a Superkey of $R$
NO escape hatch: It does not matter whether $A$ is prime or non-prime. If $X$ is not a superkey, the dependency violates BCNF and must be decomposed!
Golden Axiom of BCNF: Every determinant must be a candidate key (or superkey). In other words: "In BCNF, every arrow $X \to Y$ must have a key on its left-hand side!"
7.2

The Classic Example: 3NF Satisfied, but BCNF Violated

Consider a university course assignment relation:

STUDENT_ADVISING(Student, Course, Instructor)
Explicit Business Rules & Assumptions:
  1. For a given course, each student is taught by exactly one instructor: {Student, Course} → Instructor.
  2. Each instructor teaches only one course: Instructor → Course.
  3. A course may have multiple instructors (e.g. Prof. Sharma and Prof. Gupta both teach DBMS).
  4. A student may take multiple courses taught by different instructors.
Student (PK1) Course (PK2) Instructor Redundancy Note
Amit DBMS Prof. Sharma Prof. Sharma teaches DBMS
Neha DBMS Prof. Sharma Duplicated fact: Sharma teaches DBMS!
Amit Python Prof. Patil Prof. Patil teaches Python
Priya DBMS Prof. Gupta Prof. Gupta also teaches DBMS
Determining Candidate Keys

Closure of {Student, Course}:
$\{Student, Course\}^+ = \{Student, Course, Instructor\}$.
→ {Student, Course} is Candidate Key 1.

Closure of {Student, Instructor}:
Using $Instructor \to Course$, we get $Course$.
$\{Student, Instructor\}^+ = \{Student, Instructor, Course\}$.
→ {Student, Instructor} is Candidate Key 2!

Prime vs. Non-Prime Attributes

Attributes participating in any candidate key:

  • Student: in both keys → Prime
  • Course: in Key 1 → Prime
  • Instructor: in Key 2 → Prime
Non-prime attributes: NONE ($\emptyset$). Every attribute is prime!
Normal Form Verification Step-by-Step
Why does it satisfy 3NF?

Check both functional dependencies against 3NF rules:

  • {Student, Course} → Instructor:
    $\{Student, Course\}$ is a candidate key (superkey). ✓ Satisfies 3NF.
  • Instructor → Course:
    $Instructor$ is NOT a superkey. HOWEVER, $Course$ IS a prime attribute (member of Key 1).
    Because Condition 2 holds, ✓ Satisfies 3NF!
Why does it VIOLATE BCNF?

Check the same dependencies against the strict BCNF rule:

  • {Student, Course} → Instructor:
    Determinant is a superkey. ✓ BCNF valid.
  • Instructor → Course:
    $Instructor$ is NOT a superkey (its closure $\{Instructor, Course\} \neq R$).
    BCNF does NOT permit the prime attribute excuse!
    ✗ VIOLATES BCNF!
Anomalies Arising from the BCNF Violation:
Update Anomaly: If Prof. Sharma shifts to teaching "Data Structures", multiple student rows must be updated simultaneously, risking inconsistency.
Insertion Anomaly: We cannot record a new instructor who teaches Python until at least one student enrolls in that instructor's section.
Deletion Anomaly: If Priya drops DBMS, we might delete the only record showing that Prof. Gupta teaches DBMS.

BCNF Decomposition & Trade-off Analysis

To eliminate the BCNF violation, we decompose $R(Student, Course, Instructor)$ using the violating functional dependency $Instructor \to Course$:

R1: INSTRUCTOR_ASSIGNMENT
INSTRUCTOR_ASSIGNMENT(Instructor, Course)

Primary Key: Instructor

BCNF Valid: All attributes form Key
Verification of Properties:
  • 1. Lossless Join Property:
    $R_1 \cap R_2 = \{Instructor\}$.
    Since $Instructor \to Course$, $\{Instructor\}$ is a superkey of $R_1$.
    Therefore, $(R_1 \cap R_2) \to R_1$ holds! The decomposition is 100% Lossless.
  • 2. Dependency Preservation Property (CRITICAL LESSON):
    In $R_1$, $Instructor \to Course$ is preserved.
    In $R_2$, only $\{Student, Instructor\}$ are present.
    What happened to $(Student, Course) \to Instructor$? To check if a student has multiple instructors for the same course, we must join $R_1$ and $R_2$!
    Dependency $(Student, Course) \to Instructor$ is NOT preserved!
Theoretical Trade-off: It is always possible to find a 3NF decomposition that is both lossless and dependency-preserving. However, a BCNF decomposition is always lossless, but may NOT always preserve all functional dependencies.
7.4

Practice Exercises with Guided Solutions

Exercise 1 Candidate Key & Prime Attribute Check

Relation $R(A, B, C, D)$ has functional dependencies: $AB \to C$, $C \to D$, and $D \to A$.
Question: What are all candidate keys of $R$, and which attributes are prime?

Hint: Notice attribute $B$ never appears on the right-hand side of any dependency. Therefore, $B$ must be in every candidate key!
Solution:
1. $B$ is essential. Compute closures:
- $\{A, B\}^+ = \{A, B, C, D\}$ → Candidate key: {A, B}.
- Since $D \to A$, $\{B, D\}^+ = \{B, D, A, C\}$ → Candidate key: {B, D}.
- Since $C \to D$, $\{B, C\}^+ = \{B, C, D, A\}$ → Candidate key: {B, C}.
2. Candidate keys: {A, B}, {B, C}, {B, D}.
3. Every attribute ($A, B, C, D$) belongs to at least one candidate key! So all attributes are prime.
Exercise 2 BCNF Test

In the relation from Exercise 1 ($R(A, B, C, D)$ with keys $AB, BC, BD$), does $C \to D$ violate 3NF? Does it violate BCNF?

Hint: Is $C$ a superkey? Is $D$ a prime attribute? Remember the 3NF escape hatch vs. BCNF strict requirement.
Solution:
- 3NF check: $C$ is not a superkey, but $D$ is a prime attribute (part of key $\{B, D\}$). Thus, $C \to D$ satisfies 3NF!
- BCNF check: BCNF requires the determinant $C$ to be a superkey. Since $C^+ = \{C, D\} \neq \{A, B, C, D\}$, $C$ is not a superkey. Thus, $C \to D$ VIOLATES BCNF!
