Attributes & Keys in the Conceptual & Relational Model

NEPC42 Core Concept
1. Classification of Attributes

An attribute is a named property or characteristic that describes an entity. Attributes define what information is collected about each real-world object. In modern database design, attributes are categorized across several orthogonal dimensions:

Simple vs. Composite Attributes

Simple (Atomic): Cannot be divided into smaller sub-components. Examples: StudentID, Salary, GPA.
Composite: Can be divided into smaller sub-parts with independent meanings. Example: StudentName subdivided into FirstName, MiddleName, and LastName; or Address subdivided into Street, City, State, and Pincode.

Chen Notation: Connected hierarchy of sub-ovals stemming from the composite attribute oval.
Single-Valued vs. Multivalued Attributes

Single-Valued: Holds at most one value for a specific entity instance. Example: A student has exactly one DateOfBirth and one RollNumber.
Multivalued: May hold a set or list of multiple values for the same entity instance. Example: A student may have multiple PhoneNumbers (mobile, residence, emergency) or multiple CollegeDegrees.

Chen Notation: Represented as a Double Oval (concentrical ellipses).
Stored vs. Derived Attributes

Stored: Directly saved in physical storage because it is an immutable or fundamental fact. Example: DateOfBirth.
Derived: Calculated on-the-fly dynamically from other stored attributes or system variables. Example: Age calculated as YEAR(CURRENT_DATE) - YEAR(DateOfBirth). Storing derived attributes causes update anomalies as time passes.

Chen Notation: Represented as a Dashed Oval.
Key vs. Non-Key (Descriptive) Attributes

Key Attribute: An attribute whose values are distinctly unique for every entity in an entity set, guaranteeing uniqueness. Example: StudentID or Email.
Non-Key Attribute: Describes general characteristics where duplicates can naturally occur. Example: City, Gender, Grade.

Chen Notation: Key attributes have their names Underlined inside the oval.
2. The Hierarchy of Keys in Relational Theory

In relational theory, keys enforce entity integrity and enable efficient tuple lookup. Understanding the mathematical nesting of keys is essential:

Superkey Set (All unique identifiers)
↓ Remove redundant attributes (Minimality)
Candidate Keys (Minimal Superkeys)
↓ DBA selects the primary identifier
Primary Key (Chosen CK) Alternate Keys (Remaining CKs)
Key Type Mathematical / Relational Definition College Database Example
Superkey (SK) Any set of one or more attributes that collectively allows a tuple to be uniquely identified. May contain redundant attributes. {StudentID}, {StudentID, StudentName}, {StudentID, Email}, {Email, Phone}.
Candidate Key (CK) A minimal superkey: a superkey such that no proper subset is itself a superkey. No attribute can be discarded without losing uniqueness. In student registry: {StudentID} is a CK; {Email} is another CK. (Both are minimal).
Primary Key (PK) The candidate key chosen by the database designer as the principal mechanism of identifying tuples within the relation. Strictly NOT NULL and immutable. StudentID is selected as PK because it is compact, integer-based, and guaranteed permanent.
Alternate Key (AK) Any candidate key that was not chosen as the primary key. Still guaranteed to be unique. Email is an alternate key. (In SQL, implemented via UNIQUE NOT NULL).
Composite Key A primary or candidate key composed of two or more attributes combined. In ENROLLMENT(StudentID, CourseID, Grade): neither StudentID nor CourseID is unique alone; the composite key is {StudentID, CourseID}.
Foreign Key (FK) An attribute in a child relation that references the primary key of a parent relation, enforcing Referential Integrity. DepartmentID in STUDENT references DepartmentID in DEPARTMENT.
Conceptual ER Keys vs. SQL Constraints:
In an ER diagram, a key is a purely logical, conceptual construct denoting unique real-world entities. When mapped to MySQL 8:
  • A Primary Key becomes PRIMARY KEY (col) (automatically builds a Clustered Index and rejects NULLs).
  • An Alternate Key becomes UNIQUE NOT NULL (builds a secondary unique B-Tree index).
  • A Foreign Key becomes FOREIGN KEY (col) REFERENCES Parent(col) ON DELETE RESTRICT/CASCADE.
