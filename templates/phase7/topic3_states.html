Transaction States & Lifecycle Management

NEPC42 Core Concept
1. The Standard Transaction State Model

During its lifetime from issuance to conclusion, a database transaction moves through a series of well-defined states. The classical textbook state machine model identifies six distinct phases:

1. Active
Execution in Progress

The initial state upon START TRANSACTION. The transaction resides here while actively executing read, write, and compute statements.

2. Partially Committed
Final Statement Executed

Reached immediately after the final statement has completed in memory, but before the commit log record is guaranteed flushed to durable disk storage.

3. Committed
Durably Recorded

The commit record is written to durable storage. Modifications are permanent and irreversible. Changes can never be undone except by a new compensating transaction.

4. Failed
Error Detected

Entered when execution can no longer proceed due to hardware failure, constraint violations (e.g., duplicate key), timeout, or deadlock abort.

5. Aborted
Rollback Finished

The transaction has finished rolling back all its tentative writes using the undo log. The database state is cleanly restored to before the transaction began.

6. Terminated
Lifecycle Complete

The final exit state. All allocated locks, internal transaction ID slots, and memory buffers are returned to the DBMS connection pool.

Implementation Nuance: Exact state terminology can vary slightly across textbooks and database engines. For example, in MySQL InnoDB's source code, internal transaction states are tracked as TRX_STATE_NOT_STARTED, TRX_STATE_ACTIVE, TRX_STATE_PREPARED (in two-phase commits / XA), and TRX_STATE_COMMITTED_IN_MEMORY.
