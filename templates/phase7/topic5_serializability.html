Schedules, Conflict Serializability & Precedence Graphs

NEPC42 Core Concept
1. Serial Schedules vs. Non-Serial Schedules

A Schedule (or history) represents the chronological sequence of interleaved operations executed by a set of concurrent transactions. A schedule is classified into two primary categories:

1. Serial Schedule
No Interleaving

Transactions run one after another in complete isolation. All operations of transaction $T_1$ execute to completion before any operation of $T_2$ begins. Serial schedules are inherently correct and anomaly-free, but suffer from low throughput.

2. Non-Serial (Interleaved) Schedule
Concurrent Interleaving

Operations from multiple transactions are interleaved in time. A non-serial schedule is deemed correct if and only if it is serializable — meaning its computational outcome is mathematically equivalent to some serial schedule.

The Three Rules of Conflicting Operations

Two consecutive operations $O_i$ and $O_j$ in a schedule are said to conflict if and only if all three conditions are satisfied:

  1. They belong to different transactions ($T_i \ne T_j$).
  2. They access the exact same data item (e.g. both access $X$).
  3. At least one of the operations is a write ($W$).
Operation Pair Conflict Status? Classification & Concurrency Implication
$R_1(X)$ and $R_2(X)$ NO CONFLICT Read-Read operations commute freely. Swapping reads does not alter values.
$R_1(X)$ and $W_2(X)$ CONFLICT Read-Write (Anti-Dependency). Swapping causes $T_1$ to see a different value.
$W_1(X)$ and $R_2(X)$ CONFLICT Write-Read (Flow Dependency). Swapping leads to dirty read anomalies.
$W_1(X)$ and $W_2(X)$ CONFLICT Write-Write (Output Dependency). Swapping changes the final persisted value.

3. View Serializability (Advanced Conceptual Depth)

While Conflict Serializability is computationally fast and easy to verify via precedence graph cycle checking ($O(V + E)$ time), it is slightly more conservative than strictly necessary. A broader class of schedules is View Serializability:

1. Initial Reads:

For each data item $X$, if transaction $T_i$ reads the initial value of $X$ in schedule $S$, it must also read the initial value of $X$ in the equivalent serial schedule $S'$.

2. Read-From Relations:

If $T_i$ reads a value of $X$ written by $T_j$ in schedule $S$, then $T_i$ must read the value of $X$ written by $T_j$ in serial schedule $S'$.

3. Final Writes:

For each data item $X$, the transaction that performs the final write on $X$ in schedule $S$ must also perform the final write on $X$ in serial schedule $S'$.

Why RDBMS Systems Use Conflict Serializability: Testing whether an arbitrary schedule is View Serializable is an NP-Complete problem! Schedules that are view-serializable but not conflict-serializable involve "blind writes" (writing a data item without reading it first, e.g. $W_1(X), W_2(X), W_1(X)$). Because blind writes are rare in typical business transactions, real-world database concurrency managers use conflict serializability (via Two-Phase Locking or Multi-Version Concurrency Control).
