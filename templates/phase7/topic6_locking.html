Lesson 6

Lock-Based Concurrency Control & Two-Phase Locking (2PL)

NEPC42 Core Concept
1. Shared Locks, Exclusive Locks & Compatibility

To prevent concurrent transactions from interfering destructively with shared data items, database engines use Locks. Before a transaction can read or modify an item, it must request an appropriate lock from the DBMS Lock Manager.

Shared Lock — S-Lock
Read-Only Access

Requested when a transaction only intends to read a data item. Multiple concurrent transactions can hold Shared locks on the same data item simultaneously (Shared reading).

Exclusive Lock — X-Lock
Read-and-Write Access

Requested when a transaction intends to modify, update, or delete a data item. Only one transaction can hold an Exclusive lock on an item. No other locks (S or X) are permitted.

Lock Compatibility Matrix
Existing Lock on Item Requested: Shared (S) Requested: Exclusive (X)
Shared (S) Compatible (Granted) Incompatible (Blocked / Wait)

2. Two-Phase Locking Protocol (2PL)

Simply acquiring locks is not enough to guarantee serializability. If transactions acquire and release locks haphazardly, anomalies can still emerge. The Two-Phase Locking (2PL) protocol enforces a strict temporal rule on lock management divided into two distinct phases:

Phase 1: Growing Phase
  • The transaction may acquire locks as needed.
  • The transaction may upgrade a Shared lock to Exclusive.
  • Rule: The transaction must NEVER release any lock during this phase!
Phase 2: Shrinking Phase
  • The transaction may release locks.
  • The transaction may downgrade an Exclusive lock to Shared.
  • Rule: Once the first lock is released, the transaction can NEVER acquire another lock!
The Four Variants of Two-Phase Locking (2PL):
1. Basic 2PL Growing then Shrinking

Guarantees conflict serializability, but vulnerable to cascading rollbacks if a transaction releases a write lock and subsequently aborts.

2. Conservative 2PL Pre-declare All Locks

Acquires ALL required locks before execution begins. Completely prevents deadlocks, but requires predicting all future data access ahead of time.

3. Strict 2PL Hold X-Locks until End

Holds all Exclusive (X) locks until COMMIT or ROLLBACK. Releases Shared (S) locks earlier. Completely prevents cascading aborts.

4. Rigorous 2PL Hold ALL Locks until End

Holds BOTH Shared (S) and Exclusive (X) locks until transaction conclusion. Ensures strict serializability: schedule order matches commit order.
