Lesson 7

Deadlocks, Wait-For Graphs & Victim Recovery

NEPC42 Core Concept
1. What is a Database Deadlock?

A Deadlock is a permanent stall condition where a set of two or more transactions are in a circular wait state: each transaction is blocked waiting for a lock that is currently held by another transaction in the cycle. Because all participating transactions are blocked waiting, none can ever progress, release locks, or commit on their own.

The Classic Two-Transaction Deadlock
Transaction T1: 1. Holds Exclusive Lock on Item X.
2. Requests Exclusive Lock on Item Y.
BLOCKED waiting for T2
Transaction T2: 1. Holds Exclusive Lock on Item Y.
2. Requests Exclusive Lock on Item X.
BLOCKED waiting for T1
Wait-For Graph (WFG) Detection

A DBMS monitors deadlocks using a directed graph called a Wait-For Graph (WFG):

  • Nodes: Each currently active transaction in the system ($T_1, T_2, \dots$).
  • Directed Edge ($T_i \rightarrow T_j$): Transaction $T_i$ is waiting for a lock currently held by transaction $T_j$.
Theorem: A deadlock exists in the system if and only if the Wait-For Graph contains at least one directed cycle!
2. Handling Deadlocks: Prevention, Detection & Victim Selection
1. Deadlock Prevention
Timestamp Ordering

Assigns monotonic timestamps $TS(T)$ on transaction start:

  • Wait-Die: If older wants lock held by younger, older waits. If younger wants lock held by older, younger dies (aborts).
  • Wound-Wait: If older wants lock held by younger, older wounds (preempts) younger. If younger wants lock, younger waits.
2. Deadlock Detection
Background Graph Scanner

The DBMS lock manager runs a background thread that periodically inspects the Wait-For Graph (or applies timeouts, e.g. innodb_lock_wait_timeout). If a cycle is detected, recovery is immediately initiated.

3. Victim Selection
Automated Rollback

The DBMS chooses one transaction in the cycle to abort based on minimal cost heuristics:

  • Fewest rows updated or inserted so far.
  • Smallest undo log generated.
  • Shortest running transaction.
Real-World MySQL 8 Implementation: MySQL InnoDB has an active deadlock detector (innodb_deadlock_detect = ON) enabled by default. When an edge creates a cycle in its internal wait graph, InnoDB automatically rolls back the transaction that modified the fewest rows and issues error ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction.
