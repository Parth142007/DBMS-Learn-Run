Lesson 8

Database Recovery, Write-Ahead Logging (WAL) & Checkpoints

NEPC42 Core Concept
1. The Write-Ahead Logging (WAL) Principle

When a database updates a row, writing the modified 16KB data page directly to physical disk immediately on every SQL statement would create catastrophic I/O bottlenecks. Instead, databases modify pages in fast system RAM (the Buffer Pool) and rely on an append-only sequential log file called the Transaction Log (Redo/Undo Log).

The Golden Rule of WAL (Write-Ahead Logging): Before any modified (dirty) data page in memory is written to durable storage on disk, the corresponding log record describing the update (with old value and new value) MUST be written and flushed (via fsync) to durable non-volatile log storage!
1. The UNDO Mechanism (Ensures Atomicity)

If a transaction crashes or aborts before reaching a durable COMMIT, the recovery manager scans backward through the log and restores all modified data items to their original old values ($V_{old}$).

2. The REDO Mechanism (Ensures Durability)

If a transaction successfully committed before the crash, but its dirty data pages were still sitting in volatile RAM buffer pool and never reached disk, the recovery manager scans forward and re-applies the new values ($V_{new}$).

The Role of Checkpoints

Without checkpoints, crash recovery would require scanning the entire transaction log from the very beginning of the database's creation (years of logs!). A Checkpoint:

  1. Forces all dirty buffer pool pages modified up to this moment to be flushed to disk.
  2. Writes a <CHECKPOINT> log record noting all currently active, uncommitted transactions.
  3. Allows the database recovery manager to discard prior log records, drastically accelerating crash recovery restart times to seconds.
